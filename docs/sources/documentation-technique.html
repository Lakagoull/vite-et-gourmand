1. Réflexions initiales et choix technologiques

1.1 Analyse du besoin

Le cahier des charges décrit une application de vente en ligne de menus de traiteur, avec quatre profils (visiteur, utilisateur, employé, administrateur), un catalogue filtrable sans rechargement, un tunnel de commande avec calcul de prix (livraison au kilomètre, remise), un cycle de vie des commandes avec notifications par e-mail, un back-office et des statistiques issues d'une base non relationnelle. Les contraintes transverses sont la sécurité, le RGPD, l'accessibilité (RGAA) et un déploiement obligatoire.

Le volume de données est faible (quelques menus, quelques centaines de commandes par an) et l'équipe cliente n'est pas technique : la solution doit être simple à exploiter, peu coûteuse et facile à maintenir.

1.3 Dépendances

Volontairement réduites au minimum (surface d'attaque et maintenance) : phpmailer/phpmailer (via Composer), Bootstrap 5.3.3 et les polices Lato / Playfair Display (hébergés localement, voir RGPD). Les extensions PHP utilisées sont pdo_mysql, mongodb, gd, mbstring et openssl.

2. Architecture de l'application

2.1 Organisation MVC

L'application suit le modèle MVC avec un point d'entrée unique (front controller) : toutes les requêtes passent par public/index.php, qui charge la configuration, démarre une session sécurisée, envoie les en-têtes de sécurité puis confie la requête au routeur.

2.3 Principes de conception

  • Séparation des responsabilités : les contrôleurs valident les entrées et vérifient les droits ; les modèles contiennent tout le SQL ; les services portent la logique réutilisable (calcul du prix, envoi d'e-mails…) ; les gabarits ne font qu'afficher.
  • Une seule source de vérité pour les prix : le service Tarification est utilisé à la fois par l'API de devis (affichage en direct) et à la validation de la commande. Le prix affiché en JavaScript n'est jamais repris tel quel.
  • Amélioration progressive : la liste des menus est rendue côté serveur et fonctionne sans JavaScript ; le JavaScript ajoute le filtrage instantané via l'API /api/menus.
  • Configuration par variables d'environnement (fichier .env en local, tableau de bord de l'hébergeur en production) : aucun secret dans le code.

4.3 Base NoSQL (MongoDB)

Collection statistiques_commandes : un document par commande, copie dénormalisée créée à la commande et mise à jour à chaque changement (statut, modification). Un schéma de validation ($jsonSchema) et deux index (commande_id unique ; menu_id + date_commande pour les filtres) sont créés par mongo-init.js.

{
  "commande_id": 2, "numero_commande": "VG-2026-0002",
  "menu_id": 2, "menu_titre": "Menu de Pâques Printanier",
  "nombre_personne": 9, "prix_total": 302.21,
  "date_commande": ISODate("2026-10-01T08:05:00Z"), "statut": "terminee"
}

Le chiffre d'affaires par menu est calculé par un pipeline d'agrégation : $match (statut ≠ annulée, menu, période) → $group par menu_id ($sum des commandes et des montants) → $sort. Une erreur MongoDB n'empêche jamais l'enregistrement d'une commande (elle est journalisée) ; le script sync-mongo.php permet de reconstruire la collection à partir de MySQL.

7. Règles de gestion

8. Sécurité

La sécurité a été traitée à chaque fonctionnalité, puis vérifiée par des tests d'attaque (voir chapitre 10).

RisqueProtection mise en place
Injection SQL100 % des requêtes avec paramètres passent par des requêtes préparées PDO, émulation désactivée (ATTR_EMULATE_PREPARES = false). Les filtres sont validés et typés (filter_var).
XSS (injection de script)Toute donnée affichée passe par la fonction e() (htmlspecialchars). Côté JavaScript, construction du DOM avec textContent (jamais innerHTML avec des données). Content-Security-Policy stricte : aucun script ni style en ligne autorisé, ressources du seul domaine.
CSRFJeton aléatoire de 256 bits par session, vérifié avec hash_equals sur chaque formulaire POST ; cookie SameSite=Lax.
Mots de passeHachage bcrypt (password_hash), re-hachage automatique si l'algorithme évolue ; politique : 10 caractères, majuscule, minuscule, chiffre, caractère spécial.
Force bruteBlocage après 5 échecs par e-mail (et 20 par IP) sur 15 minutes ; temps de réponse constant même pour un compte inexistant ; messages d'erreur identiques (pas d'énumération des comptes).
Vol de sessionCookie HttpOnly, Secure en HTTPS, SameSite ; session_regenerate_id à la connexion ; mode strict ; destruction complète à la déconnexion.
Mot de passe oubliéJeton aléatoire de 256 bits, seule son empreinte SHA-256 est stockée ; valable 1 h, usage unique, anciens liens invalidés ; réponse identique que l'adresse existe ou non.
Contrôle d'accèsAuth::exiger() sur chaque action protégée : rôle vérifié et compte toujours actif en base (un employé désactivé est déconnecté immédiatement). Un client ne peut accéder qu'à ses propres commandes (contrôle du propriétaire, sinon 404).
Élévation de privilègesLe rôle est toujours imposé côté serveur (inscription = utilisateur, création par l'admin = employé) ; les champs ajoutés dans la requête sont ignorés.
Redirection ouverteLe paramètre de retour après connexion n'accepte que des chemins internes (pas de //, pas de schéma, pas d'antislash).
Envoi de fichiersTaille limitée (3 Mo), vrai type vérifié (finfo), image ré-encodée avec GD (suppression des métadonnées et de tout contenu caché), nom aléatoire, extension imposée .jpg.
Manipulation des prixPrix, remise et livraison recalculés côté serveur à partir de la base ; le stock est vérifié sous verrou (pas de survente).
SpamChamp piège invisible et limitation d'un envoi par minute (contact, mot de passe oublié).
En-têtes HTTPContent-Security-Policy, Strict-Transport-Security, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy ; signature serveur masquée.
Secrets et erreursAccès aux bases dans des variables d'environnement (jamais dans le dépôt, .env ignoré par Git) ; erreurs détaillées affichées uniquement en développement ; connexion MySQL chiffrée (TLS) avec vérification du certificat en production.

9. Accessibilité (RGAA) et RGPD

9.1 Accessibilité

  • Contrastes calculés et conformes (≥ 4,5:1) pour toutes les associations texte / fond (voir charte graphique).
  • Structure sémantique : header, nav, main, footer, titres hiérarchisés, fil d'Ariane, aria-current sur la page active.
  • Lien d'évitement « Aller au contenu principal » ; navigation complète au clavier ; focus visible renforcé.
  • Formulaires : chaque champ a une étiquette ; erreurs listées en haut avec liens vers les champs et reliées au champ (aria-invalid, aria-describedby) ; formats attendus indiqués.
  • Information jamais portée par la seule couleur : conditions du menu avec icône et titre, statuts avec libellé.
  • Zones dynamiques annoncées (aria-live) : nombre de résultats des filtres, détail du prix.
  • Images : texte alternatif obligatoire pour la galerie ; images décoratives ignorées (alt="").
  • Graphiques : description textuelle, barres atteignables au clavier, tableau de données équivalent, adaptation au mode contraste élevé.
  • Respect de la préférence « réduire les animations » ; zones cliquables d'au moins 44 px.

9.2 RGPD

  • Minimisation : seules les données nécessaires à la commande et à la livraison sont demandées.
  • Consentement explicite aux CGV et à la politique de confidentialité à l'inscription.
  • Pages mentions légales, CGV et politique de confidentialité (finalités, durées de conservation, droits, CNIL).
  • Droit de rectification depuis l'espace client.
  • Aucun cookie publicitaire ni de mesure d'audience : uniquement le cookie de session (exempté de consentement).
  • Bootstrap et polices hébergés sur le serveur : aucune adresse IP de visiteur transmise à un CDN ou à Google Fonts.
  • Hébergement de l'application dans l'Union européenne (région Francfort).

11.2 Démarche et étapes

  1. Conteneurisation : le Dockerfile part de l'image officielle php:8.2-apache, installe les extensions pdo_mysql, gd et mongodb, place la racine web sur public/, active la réécriture d'URL, passe PHP en configuration de production et installe les dépendances Composer sans les outils de développement. Le script docker/entrypoint.sh adapte Apache au port fourni par l'hébergeur et écrit le certificat MySQL transmis en variable d'environnement.
  2. Base relationnelle : création d'un service MySQL gratuit sur Aiven ; récupération de l'hôte, du port, de l'utilisateur, du mot de passe et du certificat d'autorité. Import de schema.sql et data.sql avec php database/import.php production.env (connexion TLS ; le client MySQL de XAMPP ne gérant pas l'authentification caching_sha2_password de MySQL 8, l'import passe par PDO).
  3. Base NoSQL : création d'un cluster gratuit M0 sur MongoDB Atlas, d'un utilisateur de base, et autorisation réseau (liste d'accès IP) ; exécution de mongo-init.js (collection, validation, index) puis php database/sync-mongo.php pour copier les commandes depuis MySQL.
  4. Hébergement : sur Render, création d'un Blueprint à partir du fichier render.yaml du dépôt (service web Docker, offre gratuite, région UE, branche main). Les secrets (accès aux bases, certificat, SMTP) sont saisis dans le tableau de bord, jamais versionnés.
  5. Mise en production : fusion de develop dans main ; Render construit l'image et la déploie automatiquement. Chaque nouvelle fusion dans main redéploie l'application.
  6. Vérification : test de toutes les pages, de la connexion, des données MySQL, des statistiques MongoDB et des en-têtes de sécurité sur l'URL publique.

11.4 Limites connues et évolutions

  • Mise en veille de l'offre gratuite après 15 minutes d'inactivité (premier chargement ≈ 30 s). Évolution : offre payante « always on ».
  • Stockage éphémère : les photos envoyées en production sont perdues à chaque redéploiement. Évolution : stockage objet externe (type S3) ou disque persistant.
  • E-mails : l'envoi réel nécessite de renseigner un serveur SMTP (par exemple Brevo) dans les variables d'environnement ; sans SMTP, les e-mails sont enregistrés côté serveur.
  • Distance calculée à vol d'oiseau : un calcul d'itinéraire routier nécessiterait un service de routage.
