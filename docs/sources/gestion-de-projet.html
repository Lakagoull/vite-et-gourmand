2. Méthode de travail

2.1 Une démarche agile en Kanban

J'ai retenu une méthode agile de type Kanban, adaptée à un développeur seul : pas de cérémonies lourdes, mais un flux de travail visible, un nombre limité de tâches en cours et des livraisons fréquentes.

  • Découpage en fonctionnalités : le cahier des charges a été transformé en user stories regroupées en lots cohérents, chacun livrable et testable seul (une branche Git par lot).
  • Limitation du travail en cours : une seule fonctionnalité en développement à la fois, terminée et testée avant de passer à la suivante.
  • Définition de « terminé » : une carte n'est terminée que si le code fonctionne, que les cas d'erreur et la sécurité ont été testés, que l'affichage a été vérifié (bureau et mobile) et que la branche est fusionnée dans develop.
  • Amélioration continue : les difficultés rencontrées ont été notées et corrigées au fil de l'eau (voir partie 6).

5. Gestion du code source (Git)

5.1 Stratégie de branches

  • main : branche principale, toujours stable ; c'est elle qui est déployée automatiquement en production.
  • develop : branche d'intégration des fonctionnalités terminées et testées.
  • feature/... : une branche par fonctionnalité, créée depuis develop. Après les tests, elle est fusionnée dans develop avec --no-ff (un commit de fusion garde la trace de la fonctionnalité dans l'historique).
  • Quand develop est correctement testée, elle est fusionnée dans main, ce qui déclenche le déploiement.
gitGraph commit id: "Initialisation" branch develop checkout develop branch feature/base-de-donnees commit id: "Scripts SQL + MongoDB" checkout develop merge feature/base-de-donnees branch feature/charte-graphique commit id: "Charte + maquettes" checkout develop merge feature/charte-graphique branch feature/pages-publiques commit id: "Pages publiques" checkout develop merge feature/pages-publiques branch feature/authentification commit id: "Authentification" checkout develop merge feature/authentification branch feature/commande commit id: "Commande" checkout develop merge feature/commande branch feature/espace-employe commit id: "Espace employé" checkout develop merge feature/espace-employe commit id: "Espace admin, déploiement…" checkout main merge develop id: "v1.0 en production"

Extrait de l'historique : les fonctionnalités suivantes (feature/espace-admin, feature/deploiement, feature/import-production) suivent exactement le même cycle.

5.2 Bonnes pratiques appliquées

  • Messages de commit explicites en français : un titre court décrivant la fonctionnalité, puis la liste des changements.
  • Secrets jamais versionnés : .env et les accès de production sont exclus par .gitignore ; seul .env.example (sans valeurs sensibles) est dans le dépôt.
  • Fins de ligne normalisées (.gitattributes) pour un dépôt identique sous Windows et Linux.
  • Dépendances reproductibles : composer.lock versionné, dossier vendor/ exclu.
  • Déploiement continu : toute fusion dans main est déployée automatiquement par Render.

6. Qualité, outils et difficultés rencontrées

6.1 Assurance qualité

  • Tests par scénarios à chaque fonctionnalité : cas nominaux, cas d'erreur et tentatives d'attaque (injection, CSRF, accès à la commande d'un autre client, élévation de privilèges, faux fichier image…), via de vraies requêtes HTTP.
  • Vérifications visuelles systématiques (captures d'écran bureau et mobile) comparées aux maquettes.
  • Contrôle de cohérence des données : statistiques MongoDB comparées à un calcul direct en SQL.
  • Vérification syntaxique de tous les fichiers PHP (php -l) avant chaque commit.

6.3 Difficultés rencontrées et solutions

DifficultéSolution apportée
La politique de sécurité (CSP) interdit les styles en ligne, nécessaires à un graphique classique.Graphiques dessinés en SVG côté serveur (les dimensions sont des attributs, pas des styles), sans bibliothèque externe.
Derrière le proxy de l'hébergeur, tous les visiteurs semblaient avoir la même adresse IP (risque de bloquer tout le monde après des erreurs de connexion).Lecture de l'IP réelle dans l'en-tête X-Forwarded-For quand TRUST_PROXY est activé ; la limite par e-mail reste la protection principale.
Le client MySQL de XAMPP ne gère pas l'authentification de MySQL 8 utilisée par l'hébergeur.Script d'import en PHP (database/import.php) utilisant PDO, compatible et chiffré.
Une règle métier écrite en texte libre (« à commander 14 jours avant ») n'était pas vérifiable.Ajout d'un champ « délai de commande en jours » au menu, contrôlé à la commande.
Risque de survente si deux clients commandent le dernier menu en même temps.Transaction SQL avec verrou de ligne (SELECT … FOR UPDATE) sur le stock.
Version de PHP différente entre le poste (8.0) et la production (8.2).Code limité aux fonctionnalités de PHP 8.0 ; image Docker pour figer l'environnement de production.
Peu de commandes dans les données de démonstration, graphiques peu parlants.Ajout de commandes historiques aux prix calculés selon les règles réelles, et script de synchronisation MySQL → MongoDB.
